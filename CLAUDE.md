## Current state

The backend is built ahead through Phase 4. The UI design phase is finished (Nov 16): every screen is approved in `design/html_mockups/approved-*.html`. Phase 2 screens are in progress: the Tasks group's All, Today, Inbox, Unscheduled, Next 7 days, Routines, Completed and Cancelled screens are built, with the filter-and-sort menu, New task and the shared pickers (`features/pickers/`, also used by the detail panel's breadcrumb and the Inbox), the Calendar's Week and Month (`features/calendar/`), New event (`features/events/`, from the Calendar and an area's Add menu), the routine page with its header and step editing, New routine with the first-run state and sidebar dragging, the Routines overview (`features/routines/`, with ROUTINES in the Plan sidebar), and the project page with its Overview and Board views (`features/projects/`, `/areas/projects/:id`; projects open it everywhere); the rest is listed under Next in `docs/LOG.md`. Frontend features live in `frontend/src/features/<name>/`.

## Commands

Run these from `backend/`:

- Install dependencies: `uv sync`
- Run the API: `uv run uvicorn app.main:app --reload`
- Run all tests: `uv run pytest`
- Run a single test: `uv run pytest tests/test_db.py::test_foreign_key_violation_is_rejected`
- Lint and format: `uv run ruff check --fix .` and `uv run ruff format .`
- Type-check: `uv run pyright`
- Create a migration: `uv run alembic revision --autogenerate -m "describe the change"`
- Apply migrations: `uv run alembic upgrade head`

New models must be imported in `app/models/__init__.py`, or Alembic won't see them.

Run these from `frontend/`:

- Install dependencies: `pnpm install`
- Run the dev server (the API must also be running): `pnpm dev`
- Run all tests: `pnpm test`
- Run the browser tests (Playwright; first run `pnpm exec playwright install chromium`): `pnpm e2e`. They start their own API on 8100, on a fresh temporary database, and Vite on 5180, so they never touch the dev servers or real data. Specs live in `frontend/e2e/`.
- Run a single test: `pnpm test src/App.test.tsx -t "shows that the API is connected"`
- Lint and format: `pnpm format`
- Type-check: `pnpm typecheck`
- Regenerate the API client after any backend API change: `pnpm api:generate` (CI fails if `src/client` is stale)
- Rebuild `src/styles/tokens.css` after changing `design/tokens/*.json`: `pnpm tokens` (CI fails if it is stale). Never edit `tokens.css` by hand; HeroUI overrides go in `src/styles/heroui-theme.css`.
- Build: `pnpm build`

`just` commands don't exist yet; add them here when they do. TypeScript stays on 6.x until Hey API supports TypeScript 7, which it crashes on.

## Source documents

- `docs/project_details.md` is the spec: stack, phase roadmap, status rules, service-layer rules and a decision log. Read the relevant section before implementing a feature, and add new decisions to the log.
- `docs/schema.sql` is the settled schema. It is the reference for writing the models in Phase 1. After that, **SQLAlchemy models are the source of truth**, and every model change needs an Alembic migration.
- `docs/DOMAIN.md` holds the business rules and a list of open questions. Check those before implementing the behavior they cover.
- `docs/LOG.md` records what was done and what's next. Planned but not written yet: `docs/FEEDBACK.md`.

## Stack constraints that are easy to get wrong

- Backend: Python 3.12+ with uv, FastAPI, Pydantic v2, SQLAlchemy 2.0 (Pydantic schemas are kept separate from models), Alembic, SQLite, python-dateutil for RRULE. Quality: Ruff, Pyright, pre-commit.
- Frontend: React + TypeScript + Vite with pnpm, Tailwind v4, TanStack Query, React Router, Zustand, React Hook Form + Zod, dnd-kit. Quality: Biome.
- **HeroUI is v3**: use only the v3 docs, and there is no `HeroUIProvider`.
- Style with the design tokens, not raw colors: `bg-(--card-border)`, `type-meta`, `bg-brand-700`. A life area's `color` is a palette key (`blue`, `teal`, `rose`, `plum`, `ochre`, `terracotta`); put `data-area={areaDataAttribute(color)}` on an element and use the `--area-*` roles inside it.
- **Calendar:** Week and Month use FullCalendar 7's day-grid view only (no time grid), imported from `@fullcalendar/react/daygrid` (v7 has no separate `@fullcalendar/daygrid`; don't install v6 packages) and styled in `features/calendar/calendar.css` with no theme plugin; Quarter and Year are a custom linear calendar. Tasks have no start time or duration. The Tasks boards (Next 7 days included) are built with dnd-kit and HeroUI. Day columns load from `GET /api/week` and reorder with `POST /api/tasks/reorder`.
- **Placement rule:** a task sits on its scheduled date, else its due date, else Unscheduled. Overdue = an open task with a past due date, listed in Today.
- **Routines and routine steps never open the detail panel**; they are edited on their own page. Every other existing entity opens the detail panel, except projects, which always open their project page.
- The API client is **generated by Hey API** from FastAPI's OpenAPI (TS types and TanStack Query hooks). Regenerate it after backend API changes instead of hand-writing API code.
- AI (Phase 7) and Tauri desktop (Phase 8) come later. The app must keep working with AI turned off.

## How work is built

Build in vertical slices following the phases in `docs/project_details.md`: backend → tests → regenerate client → UI. The app should be usable after every phase. Every AI prompt change gets an eval run.

## Git workflow

- Never commit directly to `main`. Each change gets its own short-lived branch named `<type>/<short-description>`, where type is `feat`, `fix`, `docs`, `chore` or `refactor`.
- Open a PR with `gh pr create` and squash-merge it once CI passes, then delete the branch.
- CI runs on GitHub Actions (`.github/workflows/ci.yml`), and its jobs are required status checks on `main`.
- The repo is public and `main` is protected: changes must arrive through a PR, even from admins, and force pushes are blocked. Never commit secrets; put them in an ignored `.env`.

## Data model essentials

The full rules are in `docs/DOMAIN.md`; these are the ones easiest to get wrong.

### SQLite setup

- `PRAGMA foreign_keys=ON` must run on **every application connection**; use `create_db_engine` in `app/db.py`. Migrations are the one exception: they run with it off, because batch mode's `DROP TABLE` would otherwise cascade-delete child rows, and `migrations/env.py` runs `PRAGMA foreign_key_check` afterwards.
- Alembic needs `render_as_batch=True`, because SQLite can only alter tables and constraints in batch mode.
- Every model puts `AUTOINCREMENT` (from `app/models/base.py`) in its `__table_args__`, so ids are never reused; a test checks every table.
- The base mixin sets `updated_at` with `onupdate=func.now()`; the DB default only covers inserts.
- Deliberate exceptions to the timestamp convention: `routine_logs` has only `created_at`, and `status_changes` has only `changed_at`.
- The models must carry over the CHECKs, composite FKs, unique and partial unique indexes from `schema.sql`, not just the columns. Alembic's autogenerate misses some of these, so check each migration.

### Ownership

- Tasks, task templates, events, metrics and routine steps belong to **a project or a life area, never both**. Only tasks and task templates may have neither (the **Inbox**).
- A project-owned item stores its project's `life_area_id`. The composite FK `(project_id, life_area_id)` → `projects(id, life_area_id)` with `ON UPDATE CASCADE` enforces it, and moving a project moves its items. Tasks and task templates also need the CHECK that a project link comes with a life area, because SQLite skips a composite FK while any column is NULL.
- **Unlink** means clearing `project_id` so the item falls back to its life area.
- Sections belong to one project (composite FK `(section_id, project_id)`) and never move. Before deleting a section, the **service moves its tasks to unsectioned**; SQLite's `SET NULL` would also clear `project_id`.
- Nothing can be created in, moved into or restored into an archived life area or an inactive project: return 409.
- There are no priorities, goals, project groups or milestones. A task's `priority` (high/medium/low/none) is a column, not an entity.

### Status, archive and dates

- Archiving is separate from status: `archived_at` set means hidden, so queries filter on `archived_at IS NULL`. Cancelled tasks are hidden by default, with a toggle to show them.
- DB CHECKs require status and its timestamp to match (`completed_at`, `cancelled_at`), so **set both in the same UPDATE**.
- Some rules are enforced by both the DB and the service. The service validates first so the API returns a clear 4xx instead of a DB error.
- `scheduled_date`, `due_date` and similar are local calendar dates; `_at` datetimes are UTC. Event times are floating local times. Weeks start on Monday.
- Notes are Markdown in a `notes` TEXT column (max 50,000 characters).
- Derived values are never stored: project progress, target state (met/missed), event upcoming/past. Life areas have no progress.
- A routine step's daily state lives in `routine_logs`; no row means to-do, or missed once the day is over unless a `routine_pauses` row covers it.

### Cascades and undo

The status and cascade table is in `docs/DOMAIN.md` section 3. Cascades follow one flow: preview all affected items → confirm → apply in one transaction → record in `status_changes` under a `batch_id` → undo restores the batch. Checking off, cancelling or archiving a task skips preview and confirmation but is still recorded.

Undo must group a batch's rows by entity and restore all of an entity's fields in a **single UPDATE**, or the status/timestamp CHECK fails. Undo covers field changes, and removes tasks a change created (recorded with a snapshot) if they are unchanged since. Series edits, which split series and regenerate occurrences, can't be undone.

### Repeating items

- Edits and cancellations offer **this one / this and following / all**. "This and following" ends the series the day before and starts a new one.
- **Events** are expanded when a range is viewed, never stored. One-off changes live in `event_exceptions`, keyed by the occurrence's original date.
- **Task templates** hold reusable task content and subtasks, as in Notion; creating a task copies them. A template with an `rrule` is a recurring task: occurrences are rows in `tasks`, unique on `(template_id, occurrence_date)`, and can't be deleted, only cancelled. Repeat rules are validated by `app/rrules.py` (no `DTSTART`, `UNTIL` or `COUNT`; the series runs from `starts_on` to `ends_on`). Services read today's date from `app.clock.today()`; tests pin it with `monkeypatch`. Generate missing occurrences for the viewed week, from today forward, unless the template repeats from completion (one open occurrence at a time). Never recreate an existing occurrence. Paused or archived templates generate nothing. Done and cancelled occurrences never change. Recurring occurrences don't roll over; only one-off tasks do.
- **Routines** take their due days from `routine_schedules` (one row per schedule change) and their paused days from `routine_pauses`, so history never changes.
